\section[Motivation]{Motivation}
\label{sec:intro-motivation}

Tool-using large language model (LLM) systems can interpret instructions and
compose robot operations through an existing interface
\citep{ahn2022saycan,liang2023codeaspolicies}. However, they generally assume
that the target robot already exposes the required application programming
interface (API). This assumption
leaves an upstream problem unresolved: the robot-specific software behind
those tools must still be authored.

Consider an SO-101 arm described by a MuJoCo model file containing its joints,
actuators, and motion limits. The \emph{high-level controller} selects and
sequences robot operations. Using illustrative API names, it reads the current
end-effector pose through \texttt{get\_ee\_pose()} and requests a Cartesian move
through \texttt{move\_cartesian(...)}. The second call requires software that
converts the requested pose into valid joint or actuator commands. This thesis
calls the reusable caller-facing contract the
\emph{robot capability interface}. Each task-neutral operation is a
\emph{capability}. The executable implementation for one robot configuration
is the \emph{robot-specific driver}.

The driver remains robot-specific even when the task is unchanged. Joint
naming, actuator semantics, units, coordinate frames, and observations vary
across configurations. Robotics frameworks therefore still require connection,
calibration, state reading, and command writing for each new platform
\citep{lerobot2026hardware,ros2control2026hardware}. Reusing a planner or learned
policy does not remove this integration requirement.

Executable code alone cannot establish correct physical behaviour. A driver
may control the wrong joints, use incorrect units, or produce an unintended
outcome. This is an instance of the software test-oracle problem
\citep{barr2015oracle,araujo2023rasreview}. Behavioural validation therefore
requires observations of the resulting motion and interaction, assessed
against the requirements of the requested operation.

Auto-Adapter addresses these problems by making robot-specific driver
synthesis part of the LLM workflow. It generates reusable software whose
capabilities can be evaluated independently before downstream task execution.

Here, ``independent'' refers to independence from the candidate driver
implementation. A test harness records measurements directly from MuJoCo state
and applies fixed acceptance criteria to determine verdicts outside the
driver's control. Test cases and acceptance criteria are fixed before driver
synthesis and remain unchanged during generation and repair within each run.
The Design agent authors the capability specifications and tests, so this
independence does not imply independent specification authorship.

\section[Research Objectives]{Research Objectives}
\label{sec:research-objectives}

This thesis develops and evaluates Auto-Adapter for generating reusable
robot-specific drivers and assessing their ability to support downstream
tasks. Downstream tasks use Recursive Context-Aware Reasoning and Planning
(ReCAP) as the high-level planning procedure \citep{zhang2025recap}.

This aim is expressed through three research questions:

\begin{enumerate}
    \item \textbf{RQ1---Auto-Adapter driver production.}

    To what extent can Auto-Adapter produce independently validated
    robot-specific drivers that a high-level controller can use for downstream
    tasks?

    \item \textbf{RQ2---AutoAdapter-Bench.}

    \textbf{(a)} With each robot's capability interface and behavioural tests
    held fixed, how do the selected LLM configurations differ in their ability
    to produce validated drivers?

    \textbf{(b)} With each robot's validated driver, task conditions and ReCAP
    planning procedure held fixed, how do the selected LLM configurations
    differ in independently judged task performance?

    \item \textbf{RQ3---Cross-robot analysis.}

    How consistently can Auto-Adapter produce usable drivers across the
    selected robot configurations, and where does the process succeed or fail?
\end{enumerate}

\section[Research Experiments]{Research Experiments}
\label{sec:research-experiments}
\label{sec:research-programme}

The empirical programme comprises three experiments on framework operation,
model comparison and cross-robot application.

\begin{enumerate}[leftmargin=*,itemsep=1em]

  \item \textbf{Experiment 1---Auto-Adapter Framework (Chapter~3).}

  This experiment studies Auto-Adapter as an end-to-end method for constructing
  robot-facing software. The framework derives a task-neutral capability
  interface and measurable acceptance criteria from machine-readable robot
  descriptions and source-backed target tasks with reviewed pass standards.
  During Design, the agent constructs the
  corresponding simulation cases before driver generation. The cases and
  criteria remain fixed during generation and repair within each run.
  An independent test harness, termed the \emph{Harness}, executes the
  generated driver and assesses actuator-mediated behaviour from independently
  recorded simulator state. Validation diagnostics can guide bounded driver
  repair.

  Capabilities that meet the behavioural requirements become available to a
  separate high-level controller for downstream task execution. The task
  outcome is judged independently from the preceding driver validation.

  \item \textbf{Experiment 2---AutoAdapter-Bench (Chapter~4).}

  AutoAdapter-Bench compares two distinct LLM roles at the robot-software
  boundary. \textbf{(a)} In the synthesis track, each robot's capability
  interface and behavioural tests remain fixed across models and independent
  runs. The models generate and revise only the robot-specific driver
  implementation. \textbf{(b)} In the tool-use track, the
  driver and interface are already fixed and independently validated. The
  model instead operates as a high-level controller that must complete tasks
  through the supplied software boundary.

  Each track retains its own experimental unit, resource accounting, and
  trusted verdict. Their results are reported separately and are not combined
  into a single model score.

  \item \textbf{Experiment 3---Cross-Robot Evaluation (Chapter~5).}

  This experiment applies Auto-Adapter across the declared robot
  configurations while holding the model setting, generation constraints, and
  evidence protocol constant. Each run constructs a fresh capability interface,
  validation suite, and robot-specific driver before independent behavioural
  evaluation. The analysis records where an unsuccessful run terminates and
  distinguishes capability-level validation from downstream task performance.
  Revision behaviour and resource use provide additional evidence about where
  the integration process encounters difficulty.

\end{enumerate}

\section[Scientific and Industry-Relevant Contributions]
{Scientific and Industry-Relevant Contributions}
\label{sec:intro-contributions}

This thesis makes three scientific contributions to the evaluation of
LLM-generated robot software and three industry-relevant contributions to
robot integration and model selection.

The scientific contributions are as follows:

\begin{enumerate}[leftmargin=*,itemsep=0.8em]

  \item \textbf{A role-separated evaluation of LLM-based robot software.}

  Prior work commonly evaluates task completion through supplied tools or
  assesses generated robot programmes against executable tests
  \citep{liang2023codeaspolicies,hu2024codebotler,fu2026capx}. AutoAdapter-Bench
  assesses driver synthesis and driver use as separate roles, giving each a
  defined evaluation target and an independent behavioural verdict.

  \item \textbf{A source-grounded pipeline for synthesising robot-facing
  interfaces.}

  Auto-Adapter derives reusable capabilities from documented task requirements
  rather than a pre-authored capability catalogue. The resulting task-neutral
  API and measurable acceptance criteria specify the behaviour that the
  robot-specific driver must implement.

  \item \textbf{An implementation-blind validation architecture for generated
  robot software.}

  Behavioural acceptance rests on measurements and verdicts outside the
  generated driver's control. Constructing validation cases before driver
  generation separates their definition from the candidate implementation.
  During evaluation, a trusted process owns the simulator measurements,
  physical-integrity checks, and final verdict.

\end{enumerate}

The industry-relevant contributions are as follows:

\begin{enumerate}[leftmargin=*,itemsep=0.8em]

  \item \textbf{An auditable workflow for LLM-assisted robot integration.}

  The permitted robot inputs and callable interface are fixed before driver
  generation begins, and predeclared limits bound revisions within each run.
  The original implementation, measurement records and automatic verdict are
  retained. Results from subsequent measurement corrections or revisions to
  the criteria are reported as separately labelled reanalyses and distinguished
  from the original results.

  \item \textbf{Reusable robot software for downstream task execution.}

  Generated drivers expose reusable capabilities through callable interfaces,
  providing software components that high-level controllers can combine
  across tasks. The driver implementation can remain unchanged while
  task-level decisions vary.

  \item \textbf{A resource-accounted basis for role-specific LLM selection.}

  Behavioural outcomes are considered alongside resource use to inform model
  selection for driver synthesis and high-level control. Model calls, token
  use, estimated cost and wall-clock time describe resource demand, while
  revision histories and failure classes help explain unsuccessful attempts.

\end{enumerate}

The evidence is limited to the evaluated Direct-MuJoCo configurations; model
and robot comparisons are descriptive and do not establish hardware
performance, sim-to-real transfer or causal morphology effects.

\section[Thesis Structure]{Thesis Structure}
\label{sec:intro-structure}

The remainder of the thesis is organised as follows:

\begin{itemize}[leftmargin=*,itemsep=0.7em]

  \item \textbf{Chapter~2---Background and Literature Review.}
  This chapter reviews embodied AI, control hierarchies and robot interfaces
  to explain how high-level decisions connect to robot-specific execution.
  It then examines LLM-based programming, tool synthesis and behavioural
  validation, identifying the research gap addressed by Auto-Adapter.

  \item \textbf{Chapter~3---Auto-Adapter Framework.}
  This chapter presents Experiment~1 and explains how Auto-Adapter derives
  reusable capabilities and behavioural tests from robot information and
  task requirements.
  It describes driver synthesis and repair using independent MuJoCo
  validation, then examines how ReCAP reuses generated PiPER drivers
  across manipulation tasks.

  \item \textbf{Chapter~4---AutoAdapter-Bench: LLMs for Robot Drivers.}
  This chapter presents Experiment~2, comparing LLMs in driver synthesis
  with each robot's capability interface and behavioural tests held fixed.
  It separately evaluates task execution through fixed, capability-validated
  drivers, examining behavioural outcomes and resource use to inform
  model selection for each role.

  \item \textbf{Chapter~5---Cross-Robot Evaluation.}
  This chapter presents Experiment~3 through MuJoCo case studies of
  Franka Panda, LEAP Hand and Skydio X2.
  It examines capability validation and downstream task outcomes to
  identify difficulties in contact, coordinated control and validation
  coverage, while discussing the limits of cross-robot comparison.

  \item \textbf{Chapter~6---Conclusion and Future Work.}
  This chapter brings together the findings from the three experiments
  to answer the research questions and summarise the thesis contributions.
  It discusses the limits of the simulation evidence and outlines
  future work on broader behavioural validation, cross-robot evaluation
  and extension to real hardware.

\end{itemize}
