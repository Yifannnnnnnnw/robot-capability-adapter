\section{Introduction}

Large language models (LLMs) can plan robot actions
\citep{ahn2022saycan,huang2023innermonologue}, but carrying out those plans
requires robot-specific software for motion and observation. Code as Policies
generates robot programmes through supplied APIs
\citep{liang2023codeaspolicies}, while recent agentic systems revise controller
code using execution feedback \citep{tripathi2026testdriven}. This chapter turns
to the robot interface itself: how can its reusable operations and behavioural
tests be generated from task requirements? The resulting driver must then be
evaluated in simulation using observations and verdicts that remain outside its
control.

This chapter presents Auto-Adapter, an LLM-agent framework for generating
robot-specific drivers. It uses public robot documentation, a simulation model
and a task library to define reusable robot operations and their behavioural
requirements. The corresponding tests are generated and fixed before driver
synthesis, without access to the eventual implementation. A coding agent
develops the driver using simulation feedback, while a separate test harness
assesses its behaviour from independently recorded simulator state. We use
ReCAP \citep{zhang2025recap} as the high-level controller to select and compose
these operations for robot task execution.

Here, a capability specifies a reusable robot operation and its expected
behaviour, while a driver provides its robot-specific Python implementation.
For example, \texttt{p \ensuremath{\leftarrow} driver.get\_ee\_position()}
invokes an observation capability, followed by
\texttt{driver.move\_cartesian(p + [0.05, 0, 0])} to invoke a motion capability,
with positions expressed in metres. The driver implements the first call by
reading the robot state and the second by computing and applying actuator
commands.

The empirical objective is to assess whether Auto-Adapter can generate
robot-specific drivers that satisfy defined behavioural requirements and
support downstream robot tasks. Behavioural tests examine whether invoking
each capability through the generated driver produces its specified outcome
in simulation. Task success under ReCAP is assessed separately, preserving
the distinction between implementing robot operations and using them to
complete a task. The practical motivation is to reduce the robot-specific
implementation work required of researchers developing high-level LLM
controllers.

\section{Background}

\subsection{Reusable Robot Capabilities}

Driver synthesis requires a description of the behaviour to be implemented.
A reusable capability expresses an operation that can contribute to several
tasks while leaving their sequencing to a higher-level controller. SkiROS2
illustrates how conditions attached to robot skills support their composition
\citep{mayr2023skiros2}. Code as Policies likewise composes robot programmes
through supplied perception and control APIs \citep{liang2023codeaspolicies}.
For driver synthesis, the further problem is to implement the operations
exposed through such an interface.

A capability therefore needs more than a function signature. For example, a
Cartesian positioning operation must define how its target is interpreted and
what reaching that target means. The same operation can support approaching
an object or positioning a gripper without encoding either complete task.
This motivates deriving reusable operations and their behavioural requirements
from the tasks they must support.

\subsection{Execution-Guided Driver Synthesis}

Implementing an operation requires connecting its intended effect to the
selected robot's control facilities. A positioning request depends on the
robot's joint structure, actuator mapping and coordinate conventions. Errors
in these mappings may produce incorrect motion even when the code executes
without an exception. Execution feedback can therefore inform revisions that
source inspection alone may not resolve. \citet{tripathi2026testdriven}, for
example, refine generated navigation controllers using diagnostics from
structured tests, including evaluation in Webots.

Physics simulation provides a setting in which candidate implementations can
be executed and their effects observed. MuJoCo models articulated dynamics
and contact, allowing control commands to be related to simulated motion
\citep{todorov2012mujoco}. For a positioning operation, an observed trajectory
can reveal whether the end effector approaches the requested target. Such
observations support driver development, while acceptance still requires a
specified behavioural criterion.

\subsection{Independent Behavioural Validation}

Determining whether observed execution satisfies its intended behaviour is
the test oracle problem \citep{barr2015oracle}. For robot drivers, this requires
connecting an operation's specification to an appropriate measurement and
decision rule. A positioning test might measure whether the end effector
reaches a declared tolerance within an allowed interval. A successful return
value alone does not establish that outcome.

This thesis consequently treats independent assessment as a requirement: the
candidate implementation must not control the measurements or acceptance
criteria used to judge it. Requirements must also be justified separately,
since independence cannot correct an inappropriate specification. Passing
capability tests supports behaviour under the tested conditions; completing
a downstream task additionally depends on how operations are selected and
composed. These distinctions motivate separating capability design, driver
implementation and behavioural assessment in the framework that follows. The
resulting simulation evidence does not establish hardware performance.

\subsection[Closed-Loop Planning with ReCAP]{Closed-Loop Planning with ReCAP}
\label{sec:recap}

Closed-loop task execution requires the LLM to interpret observations in
relation to goals that remain unresolved. A failed grasp, for example, may
require revising the next action while preserving the overall placement goal.
AutoAdapter-Bench uses Recursive Context-Aware Reasoning and Planning (ReCAP)
to organise this process. ReCAP generates an ordered subtask list and
recursively decomposes the first unresolved item until an executable action is
reached \citep{zhang2025recap}. In this chapter, these actions are capability
calls executed through each robot's fixed, validated driver.
Figure~\ref{fig:chapter3-recap-backtracking} shows how the parent plan is
revisited after subtask execution, with the updated context guiding further
refinement.

ReCAP fixes the planning procedure and context updates, while the LLM
determines the subgoals and how the remaining plan is revised. The Harness
determines task success from independently recorded simulation state; the
controller's declaration of completion is not sufficient.

\section{Auto-Adapter Framework}

\subsection{Framework overview}

Auto-Adapter runs in six stages: Study, Design, Generate, Validation, Export
and Demo. The pipeline takes robot documentation, the robot's MJCF model files
and a task library as inputs.
Figure~\ref{fig:autoadapter-framework-workflow} shows the stage sequence and
the feedback path from Validation to Generate.

\textbf{Study.} The agent reads the robot documentation and inspects the MJCF
to identify the joints, actuators and control conventions. It records these
findings in \texttt{study.json}, which supplies the robot-specific information
used during capability design and driver synthesis.

\textbf{Design.} The agent translates task requirements into reusable robot
capabilities and specifies how their effects will be measured in simulation.
Using the robot study and MJCF model, it develops the capability interface and
corresponding simulation cases within one bounded ReAct loop. The framework
checks these outputs and prepares the cases for subsequent driver validation.

\textbf{Generate.} The agent writes \texttt{driver.py} to implement the
capability interface established during Design. Generation can proceed from
scratch or use a task-neutral controller skeleton suited to the robot's
morphology. Examples include damped least-squares (DLS) inverse kinematics (IK)
for serial arms and proportional--derivative (PD) gait control for quadrupeds.
Through \texttt{execute\_python}, the agent runs the draft in development
simulations and inspects the resulting robot state and execution errors. It
revises the implementation using this feedback before submitting the driver
to Validation.

\textbf{Validation.} The validator checks each capability in fresh MuJoCo
simulations, using independently recorded simulator state and the pass criteria
established during Design.
For example:
\[
\texttt{driver.move\_cartesian}(\mathbf p^\star),
\qquad
\left\|\mathbf p_{\mathrm{ee}}(T)-\mathbf p^\star\right\|_2
\leq \varepsilon,
\]
where \(\mathbf p^\star\) is the requested target,
\(\mathbf p_{\mathrm{ee}}(T)\) is the end-effector position recorded at the end
of execution, and \(\varepsilon\) is the specified tolerance. If any critical
test fails, generate runs again with the diagnostic messages appended. Each
revised driver is evaluated using the same tests and criteria.

\textbf{Export.} A passing driver is bundled into
\texttt{auto\_adapter\_\textless robot\textgreater\_artifacts/} together
with the MJCF, the study and validate reports, and a generated README.
Self-contained artifacts run on \texttt{numpy} and \texttt{mujoco} alone.

\textbf{Demo.} ReCAP uses the generated driver to execute natural-language
tasks, calling only capabilities that passed validation. It observes state
through the driver's high-level methods and plans a sequence of capability
calls, which the runtime executes and logs. For example, a pick-and-place task
involving object \(o\) and target region \(\mathcal G\) follows:
\[
\operatorname{approach}(o)
\rightarrow \operatorname{grasp}(o)
\rightarrow \operatorname{lift}(o)
\rightarrow \operatorname{place}(o,\mathcal G)
\rightarrow \operatorname{release}(o).
\]
The terminal placement condition is
\[
\mathbf p_o(T)\in\mathcal G
\;\land\;
\operatorname{released}(o,T),
\]
where \(\mathbf p_o(T)\) is the object's position at the end of execution.
Success is measured against the task's ground-truth criterion using
independently recorded simulator state and execution video, avoiding reliance
on the controller's self-report.

The following subsections explain capability and validation design, driver
synthesis, and independent behavioural assessment. They also describe bounded
repair and the use of validated capabilities for downstream task execution.

\subsection{Designing Robot Capabilities from Tasks}
\label{sec:task-grounded-capability-design}

Auto-Adapter derives the driver interface from the tasks the robot is expected
to perform. During \textbf{Design}, the agent combines task requirements with
the information collected during \textbf{Study} to identify reusable operations.
Reaching, pushing and placing share end-effector positioning, while grasping
additionally requires gripper control. The agent defines these operations as
parameterised methods and records which tasks they support. The high-level
controller selects and combines these methods into task-specific action
sequences.

For each capability, the agent \textbf{designs simulation tests and builds the
corresponding test environments in MuJoCo}. For example, a positioning test
sets the robot's initial joint configuration and calls the positioning method
with a target position. After execution, it measures the distance between the
end effector and the target and checks whether this distance is within the
specified tolerance. The agent \textbf{uses the thresholds specified in the
task libraries} where available and explicitly labels any newly proposed
values.

As shown in Figure~\ref{fig:autoadapter-framework-workflow}, \textbf{Generate}
implements the designed capabilities, while \textbf{Validation} evaluates the
driver using the prepared test scenes and criteria. The scene checks establish
whether the tests can run and provide the required measurements. Whether the
driver actually reaches the target within the specified tolerance is assessed
during Validation.

The principal output fields for \textbf{Study} and \textbf{Design} are
summarised in Appendix~\ref{sec:appendix-stage-outputs}
(Table~\ref{tab:appendix-stage-outputs}).

\subsection{Revising Drivers through Physics-Grounded Feedback}

Auto-Adapter uses simulation validation to produce feedback for driver
refinement. After \textbf{Generate} submits a candidate, \textbf{Validation}
executes its capability methods and compares independently recorded MuJoCo
measurements with the criteria established during \textbf{Design}.
For a repairable failure, the framework converts the
case diagnostics and measurement results into a message for the generation
agent. The message identifies the failed capability and reports the observed
values, comparison rules and thresholds, together with any execution errors.
For a positioning failure, this exposes the measured target error and required
tolerance, giving the agent a concrete discrepancy to investigate.

The \textbf{Repair} prompt includes this feedback alongside the public
capability contract and directs the agent to revise the existing driver. The
revised implementation is then evaluated against the same cases and criteria.
Simulation thus supplies a repeated message-feedback loop: execute the
candidate, measure its behaviour, report the discrepancy and revise the
implementation. The behavioural target remains fixed throughout the run, and
the loop ends when validation succeeds or the repair budget is exhausted.
Figure~\ref{fig:piper-stage-traces}A shows these validation--repair cycles
alongside the recorded model turns and tool interactions.

\section{Experimental Configuration}


Five independent runs will evaluate skeleton-assisted driver generation and
cross-task reuse for AgileX PiPER in MuJoCo. Each run will use a fresh agent
session and workspace, with identical robot documentation, MJCF models,
skeleton code and task requirements. The skeleton supplies generic motion and
grasp control; generated code implements robot-specific bindings and the
capability interface produced during Design.

Auto-Adapter and ReCAP will call Claude Opus 4.8, using model identifier
\texttt{eu.anthropic.claude-opus-4-8} and \mbox{\texttt{max\_tokens = 8000}}.
Neither temperature nor reasoning effort will be explicitly set. ReAct limits
will be 16 iterations for Study, 30 for Design, 22 for Generate and each
Repair, and eight for Export. Each run will permit one initial submission and
up to three repairs. ReCAP will allow at most 16 planning calls and 12
capability calls per task episode.

Each run will produce its own capability design and validation cases, checked
for coverage of the fixed task requirements. The cases and their criteria will
remain unchanged during generation and repair, with the full suite repeated
after each revision. Only drivers passing every required case will proceed to
Export and ReCAP.

Each exported driver will be evaluated unchanged on reaching, pushing and
pick-and-place at three lateral positions, \(y\in\{-0.08,0,0.08\}\)~m.
World coordinates \((x,y,z)\), measured in metres from the robot base, will
specify end-effector targets or cube centres. The reaching target will be
\((0.40,y,0.30)\). For pushing and pick-and-place, a cube with 0.03~m sides
will start at \((0.40,y,0.205)\) on a tabletop at \(z=0.19\)~m. The
respective goals will be \((0.50,y,0.205)\) and \((0.50,y,0.285)\). Only
the pick-and-place scene will include a receiving platform, with its top at
\(z=0.27\)~m. Layouts will be shared across drivers and withheld from
generation and repair. Each episode will reset the simulator and controller
context, restoring the same initial robot pose.

An evaluator separate from ReCAP will judge task success from MuJoCo state.
Reaching will require final end-effector error of at most 0.02~m. Pushing will
require contact-driven object motion ending within 0.02~m of the goal.
Pick-and-place will require grasping, lifting and release, followed by an
object--goal distance of at most 0.07~m.

\subsection{Reuse Across Manipulation Tasks}
\label{sec:piper-driver-use}

The two exported drivers were reused across three tasks and three layouts,
producing 18 executed episodes. Reaching succeeded in 6/6 episodes and pushing
in 6/6, whereas pick-and-place succeeded in 1/6
(Figure~\ref{fig:piper-generation-results}B). The other three runs did not
export a driver, so their 27 planned episodes were not executed and are
excluded from these task-success denominators.

In a separate diagnostic using the run~04 driver, replacing Claude Opus 4.8
with GPT-6 Astra as the ReCAP model increased pick-and-place success from 1/3
to 3/3. The driver, scenes, prompts and budgets were held fixed. Terminal
object--goal errors decreased from 28.10--104.17~mm to 4.67--5.84~mm
(Figure~\ref{fig:piper-generation-results}C). The three Astra episodes are
excluded from the original five-run results.

Figure~\ref{fig:piper-task-sequences} shows the same run~04 driver completing
reaching in L2, pushing in L2 and pick-and-place in L1. The corresponding
terminal errors were 0.29~mm, 5.36~mm and 28.10~mm.

\section{Discussion}

The experiment shows that generated drivers can be reused across different
tasks. The same PiPER driver successfully performed reaching, pushing and
pick-and-place, showing that its capabilities can be combined in different
ways to achieve task goals (Figure~\ref{fig:piper-task-sequences}).

Contact validation was the main barrier to obtaining a driver that passed the
complete test suite in this experiment. All unresolved cases in the final
submissions were contact tests; the observed visual-geometry binding error
and contact-pair mismatch show that contact validation requires measurements
to refer to the actual collision surfaces
(Table~\ref{tab:piper-validation-summary}).

Passing individual capability tests does not guarantee successful
pick-and-place, because the high-level planner must also provide sufficient
clearance for the carried object. The trajectory comparison in
Figure~\ref{fig:piper-recap-comparison} is consistent with high-level planning
contributing to the original transport failure. This diagnostic covers one
driver and three layouts and does not establish a general performance
difference between the models.

\section{Summary}

This chapter presented Auto-Adapter, a framework that derives reusable robot
capabilities and behavioural tests from task requirements and independently
validates driver implementations in MuJoCo. In the PiPER experiment, two of
five runs produced drivers that passed their complete validation suites; the
remaining three each passed four of five capability tests, with contact as
the only unresolved test. Successful execution of reaching, pushing and
pick-and-place shows that the pipeline can produce robot drivers for reuse
by a high-level planner under the tested conditions.

Validation in this chapter was limited to PiPER simulation experiments using
a supplied controller skeleton, so these results do not establish performance
on other robots or real hardware. Driver generation used only one model,
while the subsequent ReCAP model replacement covered only pick-and-place;
model performance in driver generation and use therefore requires systematic
evaluation. The next chapter compares models separately in these two
stages under fixed capability interfaces and acceptance criteria to examine
how model choice affects the results.
