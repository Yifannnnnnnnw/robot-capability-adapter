\section{Introduction}

Large language models support task-level robot planning, but the methods
considered here commonly rely on supplied skills, motion mechanisms, or control
APIs rather than implementing the robot-specific actuation layer
\citep{ahn2022saycan,huang2023innermonologue,liang2023codeaspolicies}. Recent
agentic systems use test, execution, or physical feedback to refine controller
and policy code
\citep{tripathi2026testdriven,xiao2026enpire,fu2026capx,lu2026aspire}.

This chapter presents Auto-Adapter, a framework that uses public robot
descriptions, a simulation model, and documented tasks to construct reusable
robot capabilities and a robot-specific Python driver. Task-Grounded
Capability Design identifies bounded operations shared across tasks; for
example, reaching and manipulation tasks may motivate an end-effector
capability whose success requires reaching and holding a target within a stated
tolerance. Before driver generation, an Independent Validation Compiler
converts these requirements into executable tests without access to the
eventual implementation. A ReAct coding agent then develops the driver by
reading permitted files, revising its artefacts, and running bounded Python and
simulation checks \citep{yao2023react}. Final acceptance uses simulator state
recorded independently of the generated code, rather than its return values or
self-reported success.

The chapter's central empirical objective is to establish whether Auto-Adapter
produces effective robot-specific drivers whose quality, operationalised as
matched-task success under the same fixed high-level controller, exceeds that
of the selected embodied-AI baselines. This comparison does not extend to
expert-written or manually tuned drivers. Its practical motivation is to reduce
integration effort and dependence on low-level robotics expertise, thereby
lowering the entry barrier for researchers specialising in high-level
language-model policies.

\section{Background}
\subsection{Cross-robot scaling}

Robotics software has long sought portability across platforms by separating
task logic from platform-specific execution. The Robot Operating System (ROS)
provided modular communication and shared software packages, while ROS 2
extended this architecture for distributed systems
\citep{quigley2009ros,macenski2022ros2}. Capability-based frameworks expose
robot functions as task-facing operations, and SkiROS2 organises these
operations into executable skills
\citep{pantano2022capabilitysurvey,mayr2023skiros2}. However, these abstractions
do not themselves supply the platform-specific control interface required by a
newly introduced robot. Auto-Adapter targets this integration step by
generating a driver behind a stable capability interface. Its longer-term aim
is to simplify future robot onboarding, whereas Experiment 3 examines this
route within a bounded simulator cohort.

of robot platforms. Differences in their physical structure motivate
robot-specific implementations behind a common capability interface.

\subsection{Physics-Grounded Feedback}

LLM coding agents use compiler and test failures as development feedback.
\citet{tripathi2026testdriven} return structured \texttt{pytest} diagnostics
that may include aggregate simulator measurements, while
\citet{kim2026physicalcorrection} use physical simulation to correct
LLM-generated tool-using primitives. The Auto-Adapter experiment asks whether
a bounded, candidate-visible projection of MuJoCo state adds information beyond
structured diagnostics. This public feedback remains distinct from the sealed
validation cases and final \emph{Harness} verdict, and simulator state does not
establish hardware behaviour.

\subsection{Capability Design}

Task-conditioned robot programming commonly generates the code or operation
needed for one instruction, potentially leaving other reusable operations
unexplored \citep{liang2023codeaspolicies,mu2024robocodex}. Task-Grounded
Capability Design instead supplies at least twenty source-backed tasks, without
a capability catalogue or task-to-capability mapping, and asks the model to
propose five to ten capabilities intended to cover the library. From the
associated task-level standards, the model also forms capability-level pass
criteria. An implementation-blind IVC audits whether those criteria preserve
source obligations, binds them to private MuJoCo task instances and trusted
measurement definitions, and compiles an executable validation suite; the
\emph{Harness} retains final verdict authority. This design is intended to give
the high-level controller a broader set of independently testable operations
to select and compose.

\section{Auto-Adapter Framework}

\subsection{Framework Structure and Agent Workspace}

Auto-Adapter generates a robot-specific Python interface, referred to here as
a driver, through which a task-level controller can invoke reusable robot
capabilities. Its inputs comprise public robot documentation, the fixed MuJoCo
model used throughout a run, and task definitions whose requirements are
traceable to public sources. The generated driver is not itself a task policy.
Instead, it provides bounded robot operations that a separate controller may
select and compose.

Interactive simulation can help an agent develop the driver, but the generated
code should not control the evidence used to assess it. Auto-Adapter therefore
separates three responsibilities: defining the required capabilities,
implementing them for a particular robot, and assessing their physical effects.
Capability requirements and validation cases are fixed before driver
generation. The candidate driver cannot modify the observations, criteria, or
verdict used in its assessment.

The workflow applies this separation in a fixed order. It first studies the
robot and simulation model before defining any capabilities. Task-Grounded
Capability Design then derives reusable operations from the documented task
requirements, after which an independent compiler constructs the corresponding
behavioural tests. Driver synthesis implements the resulting capability
interface. Independent capability assessment determines which operations may
subsequently be used in downstream task demonstration.

Figure~\ref{fig:autoadapter-framework-workflow} traces this five-stage workflow
from declared inputs to downstream task demonstration. Robot metadata, the MJCF
model, and the task library feed study and capability design, while approved
prior-run Experience is optional. During driver synthesis, the candidate may
inspect files, revise \texttt{driver.py}, and use bounded development
simulation. Independent assessment then runs the frozen driver in fresh MuJoCo
tests and owns the capability verdict. Only accepted capabilities proceed to
task demonstration; the dashed Repair path returns bounded feedback without
exposing or changing the fixed validation cases.

Each stage in which the language model authors an artefact uses a ReAct process
that alternates between reasoning, tool use, and revision
\citep{yao2023react}. The common interface provides
\texttt{read\_file} for inspecting permitted inputs,
\texttt{write\_file} for revising the current artefact, and
\texttt{execute\_python} for bounded Python and MuJoCo execution. Results and
execution errors return to the same conversation, allowing the agent to revise
its work in response to observed behaviour.

The initial robot-study stage, termed STUDY, establishes the information needed
by the later stages. The agent examines the public documentation and fixed
simulation model to determine how the robot is actuated, which limits and
coordinate conventions apply, and which model elements provide observable
evidence of motion. Bounded simulation probes may confirm how the model
responds to actuator commands. The resulting \texttt{study.json} records these
findings and unresolved implementation risks before either the capability
contracts or driver code are written.

\subsection{Task-Grounded Capability and Validation Design}

Task-Grounded Capability Design uses the robot study and documented task
requirements to define between three and ten reusable capabilities. Each
capability represents one composable physical effect and accepts a bounded,
task-neutral request. The design also records which tasks motivate each
capability and why. This relationship supplies coverage rationale rather than
a call sequence, waypoint plan, or complete task policy. The resulting
contracts are retained in \texttt{capability\_design.json}.

For example, reaching above an object, positioning a gripper for grasping, and
moving an object towards a destination all depend on controlled Cartesian
positioning. These requirements may motivate an end-effector capability that
accepts a target position. Its criterion can require the simulated end
effector to enter and remain within a stated tolerance of that target. The
capability therefore captures a reusable physical effect without embedding the
identity or action sequence of a particular task.

Before driver synthesis, the Independent Validation Compiler translates each
capability criterion into executable simulation cases. It receives the
capability design and the withheld information needed to initialise and
observe each simulation, but it cannot inspect the candidate driver or its
later revision history. For every capability, it constructs one nominal case
representing ordinary use and one calibrated-boundary case near the declared
operating limit. For the end-effector example, these could place one target
well within the workspace and another near its declared boundary while
retaining the same behavioural criterion.

Before a formal suite is fixed, an independently prepared reference
implementation executes every compiled case. This positive control establishes
that the reference implementation can satisfy the cases under the fixed
simulation conditions. It does not provide the later generation agent with the
reference implementation or its outputs. The resulting
\texttt{capability\_validation\_suite.json} is then fixed and withheld from
driver synthesis and Repair.

\subsection{Driver Synthesis and Physics-Grounded Feedback}

Driver synthesis begins from an interface-only \texttt{driver.py} that defines
the required construction function and capability signatures. It contains no
robot-specific actuator mapping, controller implementation, task dispatch, or
validation logic. Using the same ReAct tools, the agent develops the
robot-specific implementation and runs bounded Python and simulation checks.
The generated driver remains responsible for translating capability requests
into actuator commands for the selected robot.

The framework supports two driver-generation modes. In the
\textbf{from-scratch mode}, the ReAct agent constructs the controller and
capability implementation, including the robot-specific actuator mapping and
required state handling, from the permitted robot artefacts and development
simulations. In the \textbf{skeleton-assisted mode}, the agent may additionally
inspect task-neutral controller structures suited to the robot family, such as
a generic Cartesian controller for a serial arm. These skeletons provide
reusable control structure but contain no robot-specific joint or actuator
mapping, task identity, private validation criteria, reset state, or verdict
logic. Both modes implement the same capability contract and are assessed
through the same independently compiled validation process. The experimental
design specifies which mode is used in each study.

Generation follows a write--run--observe--revise loop. The agent may execute
its draft in bounded development simulations and inspect the resulting robot
state. Import errors, unexpected actuator responses, contacts, and measured
tracking errors can therefore inform the next revision. These observations
support implementation development, but they cannot determine acceptance
because the development environment does not contain the withheld validation
cases.

During execution, a motion-producing capability reads the current
\texttt{mujoco.MjData}, computes an actuator command from the observed state
and public request, and writes the command through \texttt{data.ctrl}.
Subsequent MuJoCo steps produce the evaluated trajectory
\citep{todorov2012mujoco}. This state-dependent interaction allows the
controller to respond to tracking error as the simulation evolves rather than
relying solely on a fixed command sequence.

\subsection{Independent Assessment, Repair, and Task Demonstration}

Each capability case executes the generated driver in an isolated process. The
evaluation creates a fresh \texttt{mujoco.MjModel} and
\texttt{mujoco.MjData} from the fixed model and applies the prescribed initial
state. An evaluator outside the generated code records the actuator controls
and resulting joint trajectory directly from MuJoCo, including
\texttt{qpos}, \texttt{qvel}, and \texttt{ctrl}. Where required by a
criterion, it also records relevant body or site poses and contacts.

The evaluator applies the criteria compiled before driver synthesis. Driver
return values, printed messages, and self-reported success do not constitute
behavioural evidence. The evaluator also checks that observed motion results
from actuator commands and subsequent MuJoCo simulation steps. A case is
rejected if the candidate directly overwrites evaluated state variables instead
of producing motion through the actuator interface and simulated physics.

When a case fails, a bounded repair stage, termed Repair, receives the previous
driver and a report summarising the request, observed outcome, and relevant
diagnostics. It does not receive the executable checker or other withheld case
information. The agent may revise only the driver through the same public
development interface, after which the revised implementation is assessed
against the same fixed cases. The experimental design specifies the number of
permitted revisions.

Capability assessment and downstream task completion remain separate. A
capability becomes available for task demonstration only when both its nominal
and calibrated-boundary cases pass. Capabilities that fail either case remain
unavailable, and passing a subset is not reported as validation of the complete
driver. A separate task-level controller may then compose only the available
capabilities when attempting the documented tasks.

Task completion is judged independently from the recorded MuJoCo trajectory
and continuous execution video rather than from the controller's declaration
that it has finished. This task-level verdict does not alter the preceding
capability results and cannot trigger Repair within the same run. An optional
post-run analysis stage, termed Evolution, may propose a human-reviewed
Experience record for use in a later independent run. It cannot modify the
driver or verdicts of the originating run, and the experimental design states
whether this stage is enabled.

The resulting evidence supports claims about capability execution and task
completion only under the specified MuJoCo model, requests, initial conditions,
and measurement criteria. It does not establish hardware performance,
deployment safety, or sim-to-real transfer.

All runs use Claude Sonnet 4.6 under the same skeleton-assisted generation
condition and execution limits. Within each robot, the task, capability design,
simulation assets and private validation suite remain unchanged. Every run uses
a fresh model conversation, workspace and simulator reset. No information is
transferred between runs.

The validation suites define 58 capabilities and 116 test cases. A test case
invokes one capability with specified inputs from a fixed initial state. An
independent evaluator measures the resulting state and motion in the physics
simulator. It then applies a numerical pass criterion. Each capability has two
cases: one representative request and one request near its permitted operating
limit.

A driver qualifies only if all its test cases pass. Capabilities that pass both
cases are made available for task execution. If none passes, the task is
recorded as not run. Task success is reported separately from complete-driver
qualification.

All 33 runs remain in the denominator. Early termination is reported with its
stage and reason. Results are summarised for each robot and for the experiment
as a whole. The analysis is descriptive because the tasks and simulation
environments differ between robots.


\section{Interpretation and Limitations}

Auto-Adapter's principal methodological choice is to separate capability
design, driver implementation, and behavioural judgement. Task-Grounded
Capability Design connects a task-neutral interface to source-backed task
requirements, while the Independent Validation Compiler defines executable
cases without access to candidate code. The trusted \emph{Harness} then applies
fixed criteria to measurements recorded outside the candidate. This arrangement
prevents driver return values and self-reported completion from determining
acceptance. It does not remove judgement from translating task standards into
capability criteria or make the resulting suite exhaustive.

The evidence produced at each stage answers a different question. Source and
import checks establish only that a candidate can be loaded. A Capability
Validation pass supports the declared physical effect for the exact nominal and
calibrated-boundary cases; those two cases do not cover every request,
interaction, or long-horizon composition. A Task Demo evaluates downstream
composition using only capabilities that passed both cases. Its outcome neither
changes the earlier capability verdicts nor establishes that the complete
driver passed. Similarly, a terminal pass after Repair measures performance
after bounded feedback and must remain distinct from initial-attempt
performance.

The framework definition alone does not establish that Auto-Adapter reliably
produces effective drivers, outperforms alternative methods, or generalises
across robot configurations. Those questions require the controlled
evaluations in later chapters. Furthermore, Direct-MuJoCo evidence is
conditional on the selected assets, requests, initial states, observation
operators, and thresholds. It does not measure real-SDK fidelity, sensing
uncertainty, communication latency, calibration error, hardware safety, or
sim-to-real transfer. Cross-configuration outcomes must remain descriptive
because morphology, actuation, task catalogue, scene, and observation
facilities vary together.

\section{Summary}

This chapter defined Auto-Adapter as a framework for constructing a reusable,
robot-specific Python driver from public robot information and source-backed
task requirements. It first studies the robot and fixed simulation model,
derives task-neutral capabilities, and compiles implementation-blind
behavioural cases. A bounded ReAct coding agent then implements the driver
using public MuJoCo feedback. The trusted \emph{Harness} evaluates the
resulting actuator-mediated trajectories against fixed criteria rather than
relying on candidate output.

The workflow keeps source checking, capability validation, Repair, downstream
Task Demo, and any later Experience use distinct. Only capabilities satisfying
both their nominal and calibrated-boundary cases are exposed to Task Demo, and
its terminal outcome does not rewrite driver verdicts. These boundaries provide
an auditable basis for empirical comparison; they are not themselves evidence
of universal integration or hardware readiness.
Chapter~\ref{chapter:autoadapter-bench} evaluates driver synthesis and
downstream use under controlled inputs, while
Chapter~\ref{chapter:cross-robot-evaluation} examines the complete construction
route across the declared Direct-MuJoCo configurations.
