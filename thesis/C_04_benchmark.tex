\chapter[AutoAdapter-Bench]{AutoAdapter-Bench: LLMs for Robot Drivers}
\label{chapter:autoadapter-bench}

\begin{quote}\itshape
The objective of this chapter is to present AutoAdapter-Bench, which separately
evaluates LLMs on driver synthesis and driver use. After setting out the
background and research questions, the chapter describes the benchmark and
experimental design. It then presents and discusses the results, concluding
with a summary that leads into the cross-robot evaluation in Chapter 5.
\end{quote}

\section[Introduction]{Introduction}

Comparing LLMs within Auto-Adapter requires distinguishing driver quality from
planning performance. When the LLM changes in both roles, differences in
end-to-end task success can arise from implementation, planning, or their
interaction.

HumanEval evaluates generated programs for functional correctness
\citep{chen2021codex}, whereas ProgPrompt evaluates task plans constructed from
supplied robot actions \citep{singh2023progprompt}. These approaches motivate
separate evaluation of the implementation behind an interface and the decisions
made through it. For driver synthesis, this requires a fixed behavioural
specification and a verdict based on independently recorded robot state.

AutoAdapter-Bench evaluates these capabilities separately in MuJoCo, using
SO-101 and Unitree Go2 as representatives of robotic arms and quadrupeds,
respectively. For each robot, the synthesis experiment measures how often each
LLM produces a driver that meets the same interface and behavioural
requirements. The driver-use experiment measures task completion while keeping
the validated driver, task conditions and planning procedure fixed within each
robot. The aim is to support model selection for each role within the evaluated
configurations.



\section[Background and Research Questions]{Background and Research Questions}

\subsection[Comparability in Driver Synthesis]{Comparability in Driver Synthesis}

Chapter 3 describes driver synthesis as an iterative process in which an LLM
implements a specified capability interface. Development simulations expose
the resulting robot state and execution errors, allowing the LLM to revise its
implementation before submitting the driver. Later driver submissions can
also incorporate diagnostic feedback from validation.

Execution feedback guides development, while independent behavioural
assessment establishes whether the resulting driver meets its requirements.
Passing individual tests provides evidence about specific capabilities but
does not establish conformance to the complete behavioural standard.

\subsection[Closed-Loop Planning with ReCAP]{Closed-Loop Planning with ReCAP}
\label{sec:recap}

Closed-loop task execution requires the LLM to interpret observations in
relation to goals that remain unresolved. A failed grasp, for example, may
require revising the next action while preserving the overall placement goal.
AutoAdapter-Bench uses Recursive Context-Aware Reasoning and Planning (ReCAP)
to organise this process. ReCAP generates an ordered subtask list and
recursively decomposes the first unresolved item until an executable action is
reached \citep{zhang2025recap}. In this chapter, these actions are capability
calls executed through each robot's fixed, validated driver.
Figure~\ref{fig:chapter3-recap-backtracking} shows how the parent plan is
revisited after subtask execution, with the updated context guiding further
refinement.

ReCAP fixes the planning procedure and context updates, while the LLM
determines the subgoals and how the remaining plan is revised. The Harness
determines task success from independently recorded simulation state; the
controller's declaration of completion is not sufficient.

\subsection[Research Questions]{Research Questions}

AutoAdapter-Bench therefore treats observed performance as conditional on a
fixed model-plus-endpoint configuration and experimental route, rather than as
an intrinsic property of a model family. The chapter addresses two questions:

\paragraph{\textit{RQ2a---Driver synthesis.}}
Across the selected fixed serial-arm and quadruped configurations, to what
extent do the seven LLM configurations differ in the proportion of generated
drivers that satisfy the fixed capability-level behavioural standard, and
how does providing trusted, task-neutral starter source affect that outcome?

\paragraph{\textit{RQ2b---Driver use.}}
When each robot's capability-validated driver and task conditions are held
constant, to what extent do the same seven LLM configurations differ in
independently judged complete-task success?

The first question concerns generation of the robot-facing software layer. The
second concerns downstream use of that already fixed layer. Neither experiment
compares alternative synthesis frameworks or controller architectures.

\section[AutoAdapter-Bench]{AutoAdapter-Bench}

AutoAdapter-Bench compares LLMs in driver synthesis and task execution through
supplied drivers. Its coverage spans fifteen platforms across seven embodiment
types (Figure~\ref{fig:robot-platform-taxonomy};
Table~\ref{tab:robot-platform-embodiment-types}), with SO-101 and Unitree Go2
used for the comparisons in this chapter.

Test selection follows the task-grounded capability design in
Section~\ref{sec:task-grounded-capability-design}. Reaching and placing, for
example, motivate Cartesian positioning, assessed through target error and
sustained holding. Each capability receives nominal and calibrated-boundary
cases. A separately prepared reference implementation must pass the suite to
establish feasibility; an independent evaluator then judges candidate behaviour
from recorded MuJoCo state.

For each robot, models implement the same capability interface using the
supplied documentation and simulation assets. Skeleton-assisted generation
provides DLS inverse kinematics and joint-motion control for SO-101, and a
pretrained velocity-control policy for Go2. The model supplies robot-specific
bindings and implements the required capability methods. From-scratch
generation provides textual algorithmic guidance but requires the model to
write its own control code. Both conditions permit bounded development and
revision and use the same behavioural tests. The skeleton comparison assesses
the effect of supplied control implementations within each robot, since the
arm controller and the pretrained Go2 policy provide different forms of
assistance.

The driver-use experiment varies the LLM within the ReCAP procedure described
in Section~\ref{sec:recap}. Each robot's capability-validated driver and task
conditions remain fixed, removing differences between generated
implementations from the comparison. The model selects capability calls and
revises its plan to achieve the task goal.

Synthesis success is the proportion of trials whose final submitted driver
passes the complete suite. Driver-use success is the proportion of episodes
satisfying the task completion criterion. Partial case coverage provides
diagnostic detail about synthesis failures. Runtime, token usage and estimated
cost describe resource requirements.
Section~\ref{sec:benchmark-experiment-design} specifies the model
configurations, budgets and repetitions.

\section[Experiment design]{Experiment design}
\label{sec:benchmark-experiment-design}

Experiment~2a compares driver synthesis for SO-101 and Unitree Go2. The
deployed model factor has seven configurations: Sonnet 4.6, Opus 5, Haiku 4.5,
Nova Pro, DeepSeek V4 Pro, Ministral 3 8B, and GPT-5.6 Sol. Each configuration
is evaluated under both skeleton-assisted and from-scratch generation. The
skeleton-assisted condition provides trusted, task-neutral starter source,
whereas the from-scratch condition requires the model to implement the driver
without access to that source. Within each robot block, both conditions use the
same capability interface, pass standards, and independent behavioural tests.

The experimental unit is one
robot--model--condition--replicate generation cell. Each robot--model
combination has three prespecified synthesis replicates, and paired conditions
use the same seed where the endpoint supports seed control. Their model
sessions, workspaces, and generated drivers remain isolated. Each cell permits
at most three frozen driver submissions: one initial submission and up to two
bounded corrections. The design therefore contains
$2$ robots $\times 7$ models $\times 2$ conditions $\times 3$ replicates
$=84$ cells and permits at most 252 trusted Harness validations. Cell-level
success is determined by the final frozen driver.

Experiment~2b evaluates downstream task completion rather than driver
synthesis. The same seven model configurations serve as interchangeable
backbones within one fixed ReCAP high-level planner
\citep{zhang2025recap}. Auto-Adapter supplies one fixed,
capability-validated driver and one defined capability interface for each
robot. The ReCAP logic, prompt, task conditions, driver, interface, and trusted
Harness remain fixed across episodes. Only the deployed model-plus-endpoint
configuration varies, and the Harness independently determines task success.

The SO-101 task block comprises Push to Goal, Sweep into Goal, Pick and Place,
Pick and Place with Wall, and Bin Picking. The Unitree Go2 task block comprises
Single-step Ascent, Single-step Descent, Fixed Mixed-obstacle Path, Barkour
Pause-table Transition, and Barkour Weave Poles. Robot, task, and replicate
serve as blocking dimensions rather than manipulated factors.

The experimental unit is one
robot--task--model--replicate episode. Each robot--task--model combination is
repeated three times, giving
$2$ robots $\times 5$ tasks $\times 7$ models $\times 3$ replicates
$=210$ planned episodes. Every repetition creates a fresh isolated execution
process, driver instance, and MuJoCo session, while retaining the same sealed
scene, reset, and initial state. No task-reset seed is varied. The design
therefore measures run-to-run repeatability under one fixed initial condition,
not robustness to different task seeds or starting states.

The corrected non-formal audit reported below retained the first four
SO-101 tasks and used Dial Turn in place of Bin Picking; its selected
outcomes do not replace the source formal record.
Figure~\ref{fig:chapter4-exp2b-task-scenes} groups the ten corrected-audit
scenes by robot and task family. The upper row contains five SO-101
object-interaction tasks, spanning planar pushing, sweeping, grasping,
obstacle-constrained placement, and dial rotation. The lower row contains five
Go2 locomotion tasks spanning step transitions, mixed obstacles, a table
transition, and ordered pole weaving. The image identifies the evaluated
conditions; it does not report task outcomes or replace the source formal
record.

Across all evaluable R1--R2 episodes, aggregate success was almost identical for SO-101 and Go2 (50.0\% and 49.2\%), placing the larger performance variation at task level rather than between robot platforms. Weave Poles failed in all 11 evaluable episodes because none completed the five alternating 0.12\,m waypoint regions in order (median one completed); nine nevertheless met the 0.10\,m torso-clearance requirement and all passed terminal stability. \section[Discussion]{Discussion}

Taken together, Table~\ref{tab:chapter3-exp2b-model-results} and the retained controller traces indicate that the most consequential difference was not command emission itself, but whether returned observations were used to revise an incomplete plan. In the successful Pick and Place with Wall episode, the controller recognised a failed first grasp, fully closed the gripper, and retried before following the elevated route; failed traces instead moved towards release while the object remained near its start. Weave Poles exposed a complementary long-horizon weakness: several controllers generated locally plausible motions and maintained pole separation, yet none preserved the alternating waypoint sequence across calls. This suggests that exposing ReCAP feedback is insufficient unless the model retains subgoal state and uses the observations to replan.

A second implication concerns completion judgement. Nova Pro and Ministral sometimes produced invalid controller outputs, but every normally terminated Harness failure across the cohort had nevertheless been declared complete by the controller. The trusted Harness is therefore necessary to distinguish valid capability execution and model-reported completion from externally observed task completion. Within these simulator conditions, the practically important model differences concerned feedback interpretation, multi-stage state tracking, and recovery from failed intermediate actions.

\section{Summary}

This chapter evaluated two distinct abilities at the robot--software boundary:
synthesising a reusable driver and completing tasks through an existing,
capability-validated driver. For RQ2a, no fixed-suite cell reaching the trusted
Harness achieved complete driver-level conformance. Partial behavioural
coverage nevertheless differed across model--robot configurations, reaching
14/18 cases (77.8\%) for SO-101 with Opus~5 and 14/15 cases (93.3\%) for
Unitree Go2 with Sonnet~4.6. Providing a reviewed, task-neutral driver skeleton
was therefore insufficient to ensure complete behavioural conformance.

For RQ2b, the model-plus-endpoint configurations produced markedly different
outcomes when controlling fixed drivers through ReCAP. The Harness recorded 61
successes among 123 evaluable episodes (49.6\%); model-level rates ranged from
12/12 (100.0\%) for Opus~5 to 0/20 (0.0\%) for Ministral~3~8B. Because the
evaluable denominators differed, this is a descriptive comparison rather than
a universal model ranking. Success was similar across the two robot blocks, at
30/60 (50.0\%) for SO-101 and 31/63 (49.2\%) for Go2, but varied more widely
among tasks. The retained traces suggest that unsuccessful grasp recovery,
incomplete use of returned observations, and loss of long-horizon subgoal
state contributed to task failures.

Taken together, the findings show that driver synthesis and driver use require
separate evidence. Every normally terminated Harness failure in
Experiment~2b had nevertheless been declared complete by the controller,
supporting the need for candidate-independent behavioural judgement. The
conclusions remain bounded to the selected model-plus-endpoint configurations,
fixed tasks and initial conditions, the ReCAP controller, and the evaluated
MuJoCo physics simulation, in which robot drivers issued commands directly to
simulated robots. They do not establish hardware performance, morphology
effects, or a universal model ranking.
Chapter~\ref{chapter:cross-robot-evaluation} next examines the complete
Auto-Adapter construction route across a broader robot cohort.
