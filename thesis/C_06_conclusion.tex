\section[Summary]{Summary}
This chapter answers RQ3 by analysing where the method breaks down. The goal is
to make the boundary of the thesis explicit: the harness can produce bounded
evidence for adapter correctness, but it cannot by itself guarantee all
physical robot behaviours.

\paragraph{\textit{Background literature.}}
The chapter draws on literature and practice in sim-to-real transfer, robot
runtime integration, failure analysis, calibration, sensing, and safety
engineering. These areas explain why a generated adapter can pass available
validation while still failing under physical deployment conditions.

\paragraph{\textit{Sim-to-real and physical deployment.}}
Simulator validation can expose many interface and behaviour errors, but
physical deployment introduces calibration, perception, contact, latency, and
safety constraints that may not be represented in simulation.

\paragraph{\textit{Runtime integration failure modes.}}
Runtime failures may arise from backend assumptions, transport mismatches,
camera geometry, coordinate frames, servo behaviour, calibration drift, or
observation-action inconsistency.

\paragraph{\textit{Case study materials.}}
The chapter uses runtime integration cases, validation logs, traces, robot
observations, generated adapter artifacts, and failure evidence as its study
materials. These materials are used to analyse whether failures arise from
model capability, morphology, validation coverage, runtime assumptions, or
physical deployment.

\paragraph{\textit{SO101 runtime backend integration.}}
The SO101 case study describes the backend route, bridge process, calibration
assumptions, observation path, action interface, and hardware-facing
constraints. It focuses on how the adapter contract meets the physical
execution route.

\paragraph{\textit{Additional runtime routes.}}
Additional routes such as Piper CAN, Unitree DDS, RealSense/D405 camera
bridges, or other SDK-backed systems can show that runtime backend integration
is not a single-robot special case.

\paragraph{\textit{Aims of study and analysis approach.}}
The aim of this chapter is to classify boundary conditions and failure modes.
The analysis asks whether each failure is best explained by model capability,
robot morphology, validation coverage, runtime integration, or physical
deployment constraints.

\paragraph{\textit{Failure categorisation.}}
Failures are categorised by source so that the thesis can distinguish
generation errors from tool-use errors, validation gaps, backend mismatches,
and physical-world constraints.

\paragraph{\textit{Boundary analysis.}}
Boundary analysis identifies what the current method supports and what remains
outside its evidence base. This makes the thesis contribution grounded rather
than overclaimed.

\paragraph{\textit{Failure and integration analysis.}}
Failure evidence may include false validation, grasp failures, servo bias,
hand-eye or calibration errors, near-field depth issues, transport mismatches,
and observation-action inconsistencies.

\paragraph{\textit{Model and morphology boundaries.}}
Some failures arise because a model cannot infer the correct adapter structure,
while others arise because a morphology or control interface makes the adapter
problem more difficult.

\paragraph{\textit{Validation gaps.}}
Validation gaps occur when available checks fail to expose a behaviour that
later matters during downstream execution or physical deployment.

\paragraph{\textit{Runtime backend boundaries.}}
Runtime backend boundaries occur when the adapter contract does not fully
capture assumptions made by the SDK, bridge, camera, calibration file, or
transport route.

\paragraph{\textit{Results.}}
The chapter reports failure categories, validation gaps, repaired and
unrepaired cases, and lessons for extending simulator validation toward
physical deployment.

\section[Contributions]{Contributions}
The boundary analysis clarifies what the thesis does and does not claim. The
current work supports simulator-grounded and harness-gated onboarding of robot
runtime adapters, while stronger physical validation, hardware safety review,
and deployment-specific engineering remain future work.

\paragraph{\textit{Interpretation of results.}}
The results should be interpreted around the thesis claim that formal
robot-and-runtime contracts make adapter synthesis more reusable and that
validated adapters can become useful tool layers for downstream agents. At the
same time, the failure evidence shows that model capability, robot morphology,
validation coverage, and runtime integration remain important constraints.

\paragraph{\textit{Limitations of current validation.}}
The validation procedures are useful as feedback and evidence, but they are not
complete guarantees of physical success. False validation is especially
important because it shows where a generated adapter can pass available checks
while still failing under real robot conditions.

\paragraph{\textit{Final conclusion.}}
The thesis reframes robot-facing LLM tool construction as a reusable adapter
synthesis problem. It argues that the key unit is not a one-off task script,
but a runtime adapter whose interface can be specified, validated, reused, and
called by downstream agents.

RQ1 is answered through the benchmark evaluation of reusable adapter synthesis.
RQ2 is answered through downstream task execution with validated adapters as
tool layers. RQ3 is answered through the failure categories and limitations
that reveal the boundary between current validation procedures, runtime
integration, and physical deployment.

The broader implication is that robotics-oriented LLM systems need
infrastructure that connects formal specifications, backend execution routes,
and empirical evidence. The harness provides that structure while leaving room
for more capable agents and stronger physical validation in future work.

\section[Further Work]{Further Work}
Future work includes richer diagnosis and repair agents, video-based
diagnosis, automated reward or oracle construction, broader backend coverage,
stronger physical safety constraints, and better integration between adapter
synthesis and downstream task execution.
