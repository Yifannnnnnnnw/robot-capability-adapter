\chapter[AutoAdapter-Bench]{AutoAdapter-Bench: LLMs for Robot Drivers}
\label{chapter:autoadapter-bench}

\begin{quote}\itshape
This chapter presents AutoAdapter-Bench, a benchmark for comparing how
different LLM backbones perform in robot-driver tasks. The benchmark separates
two abilities that are often conflated: synthesising robot-specific drivers and
using robot capability interfaces to complete tasks.
\end{quote}

\section[Introduction]{Introduction}

A robot policy or large language model (LLM) can operate a particular robot
only through robot-specific software. This software translates requested
operations into commands understood by the simulator, robot controller, or
vendor software development kit. This thesis uses the term \emph{driver} for
a reusable Python interface that implements defined motion, sensing, and
lifecycle capabilities for one robot. An LLM may help by generating this
software or by planning through an existing driver, but success in one role
does not establish success in the other.

This distinction creates a practical evaluation problem. Driver generation
must be judged from independently observed behaviour rather than source code
alone. Driver use must instead be judged by whether a controller completes a
task through capabilities that already exist. Combining these outcomes would
hide whether a model failed to construct the robot-facing software or failed
to use it effectively.

The declared AutoAdapter-Bench cohort contains seven LLM configurations and
eleven robot configurations across five robot types: fixed serial arms,
quadrupeds, dexterous hands, mobile manipulators, and bimanual manipulators.
This breadth describes the range of robot configurations represented in the
benchmark; it does not imply that every configuration has been evaluated in
every experiment. Chapter~3 selects SO-101 and Unitree Go2 as contrasting
representatives of fixed-arm manipulation and quadruped locomotion. Their
different control requirements provide a bounded comparison across two robot
types without treating morphology as an experimental effect.

Against this background, the chapter asks how the seven LLM configurations
differ in two roles. The first is generating a driver that satisfies fixed
capability-level behavioural requirements. The second is completing a robot
task through an existing, capability-validated driver. The two roles are
evaluated separately on the selected arm and quadruped configurations.

The experiments therefore retain separate statistical units, success
criteria, and results. Their evidence is limited to the declared model
endpoints, the two selected robot configurations, the declared
physics-simulation route, and the fixed protocols. It does not establish
hardware performance, effects of robot morphology, or a universal model
ranking. The remainder of the chapter defines the research questions before
describing the benchmark design, the two experiments, and their separate
findings.

\section[Background and Research Questions]{Background and Research Questions}

Code-generation benchmarks commonly evaluate whether model-produced programs
pass executable tests, whereas many LLM-based robot controllers assume that
actions or tools are already available and assess planning or task completion
\citep{chen2021codex,jimenez2024swebench,ahn2022saycan,
singh2023progprompt}. Neither setting alone reveals how a model performs when
constructing a robot-specific driver and when operating through an existing
driver.

AutoAdapter-Bench therefore treats observed performance as conditional on a
fixed model-plus-endpoint configuration and experimental route, rather than as
an intrinsic property of a model family. The chapter addresses two questions:

\paragraph{\textit{RQ1a---Driver synthesis.}}
Across the selected fixed serial-arm and quadruped configurations, to what
extent do the seven LLM configurations differ in the proportion of generated
drivers that satisfy the fixed capability-level behavioural standard, and
how does providing trusted, task-neutral starter source affect that outcome?

\paragraph{\textit{RQ1b---Driver use.}}
When each robot's capability-validated driver and task conditions are held
constant, to what extent do the same seven LLM configurations differ in
independently judged complete-task success?

The first question concerns generation of the robot-facing software layer. The
second concerns downstream use of that already fixed layer. Neither experiment
compares alternative synthesis frameworks or controller architectures.

Experiment~1b evaluated whether fixed, capability-validated robot APIs
supported downstream task completion. Seven LLMs were compared as
interchangeable backbones within the same ReCAP high-level planner
\citep{zhang2025recap}. Auto-Adapter supplied one fixed driver and capability
interface for SO-101 and Unitree Go2. Each model was evaluated on five tasks
per robot with three repetitions, yielding 210 episodes. The driver,
interface, planner logic, task conditions and evaluator were held constant;
only the LLM backbone varied. Task success was determined independently by
the trusted Harness. The available capabilities are summarised below.

The SO-101 tasks are Push to Goal, Sweep into Goal, Pick and Place, Pick and
Place with Wall, and Bin Picking. The Unitree Go2 tasks are Single-step
Ascent, Single-step Descent, Fixed Mixed-obstacle Path, Barkour Pause-table
Transition, and Barkour Weave Poles. Robot and task are blocking dimensions in
Experiment~1b rather than manipulated factors.

Each robot--task--model combination is repeated three times. The fixed task
definitions do not vary a reset seed, so all three repetitions use the same
sealed scene, reset, and initial state. Each repetition nevertheless creates a
fresh isolated execution process, driver instance, and MuJoCo session. MuJoCo
is the physics simulator used in this study. The design thus measures
run-to-run repeatability under one fixed initial condition, not robustness
across different task seeds or starting states.

Across all evaluable R1--R2 episodes, aggregate success was almost identical for SO-101 and Go2 (50.0\% and 49.2\%), placing the larger performance variation at task level rather than between robot platforms. Weave Poles failed in all 11 evaluable episodes because none completed the five alternating 0.12\,m waypoint regions in order (median one completed); nine nevertheless met the 0.10\,m torso-clearance requirement and all passed terminal stability. Pick and Place with Wall was limited by failed grasp recovery before wall traversal: across all eight evaluable failures the object rose by at most 7.1\,mm and moved at most 2.9\,cm from its start while contact integrity remained valid, whereas the sole success recognised an unsuccessful first grasp, issued a fully closed re-grasp, and then followed the elevated route.

\section[Discussion]{Discussion}

Taken together, Table~\ref{tab:chapter3-exp1b-model-results} and the retained controller traces indicate that the most consequential difference was not command emission itself, but whether returned observations were used to revise an incomplete plan. In the successful Pick and Place with Wall episode, the controller recognised a failed first grasp, fully closed the gripper, and retried before following the elevated route; failed traces instead moved towards release while the object remained near its start. Weave Poles exposed a complementary long-horizon weakness: several controllers generated locally plausible motions and maintained pole separation, yet none preserved the alternating waypoint sequence across calls. This suggests that exposing ReCAP feedback is insufficient unless the model retains subgoal state and uses the observations to replan.

A second implication concerns completion judgement. Nova Pro and Ministral sometimes produced invalid controller outputs, but every normally terminated Harness failure across the cohort had nevertheless been declared complete by the controller. The trusted Harness is therefore necessary to distinguish valid capability execution and model-reported completion from externally observed task completion. Within these simulator conditions, the practically important model differences concerned feedback interpretation, multi-stage state tracking, and recovery from failed intermediate actions.
