\chapter[Harness Control for Robot Adapter Synthesis]{Harness Control for Robot Adapter Synthesis}\label{chapter:harness}

\begin{quote}\itshape
This chapter presents Exp. 1. It tests whether a harness pipeline can
make robot runtime adapter synthesis bounded, inspectable, and separable from
open-ended robot code generation.
\end{quote}

\section[Introduction]{Introduction}
This experiment examines whether robot runtime adapter synthesis can be
controlled as a supervised pipeline rather than as ad hoc code generation. The
chapter asks what must be specified before an LLM coding agent writes adapter
code, how the harness should constrain and observe the agent, what validation
gates should be applied before the adapter is used downstream, what evidence
should be produced after generation, and where responsibility should sit
between the generated adapter and the surrounding harness.

\section[Background Literature]{Background Literature}
The experiment draws on literature and practice from robot software
architectures, middleware, software contracts, generated code validation, and
tool-using LLM systems. These areas motivate the need for a boundary between
the generated adapter, the runtime backend, and the validation system.

\subsection[Robot Runtime Interfaces]{Robot Runtime Interfaces}
Robot runtime interfaces expose platform-specific execution routes such as
simulator APIs, vendor SDKs, CAN bridges, DDS routes, HTTP services, camera
drivers, and calibration files. A reusable adapter must translate stable
primitive semantics into these concrete backend calls.

\subsection[Contracts and Interface Specifications]{Contracts and Interface Specifications}
Contracts define the assumptions under which generated code is allowed to
operate. In this thesis, contracts include morphology, units, coordinate
frames, primitive signatures, backend routes, approved SDK surfaces, safety
limits, and expected evidence artifacts.

\subsection[Validation and Evidence in Generated Code]{Validation and Evidence in Generated Code}
Generated code requires validation that is independent from the model that
authored it. This background motivates the harness design: validation should
produce structured evidence, not only a binary success label.

\section[System Inputs and Artifacts]{System Inputs and Artifacts}
The experiment uses runtime profiles, robot descriptions, primitive contracts,
backend constraints, generated adapter files, validation reports, logs, and
evidence artifacts as its main materials. These artifacts define the boundary
between what the LLM may generate and what the harness must control.

\subsection[Runtime Profiles and Robot Specifications]{Runtime Profiles and Robot Specifications}
Runtime profiles describe the robot binding, simulator or hardware route,
available packages, backend API, action and observation surfaces, and safety
constraints. Robot specifications provide morphology, joint limits,
end-effector definitions, gripper semantics, and sensing assumptions.

\subsection[Adapter and Evidence Artifacts]{Adapter and Evidence Artifacts}
The generated adapter is the main output of the coding agent. Evidence
artifacts include validation reports, source checks, primitive test results,
transport traces, composition smoke tests, and optional qualitative evidence
from downstream execution or diagnosis roles.

\section[Aims of Study and Analysis Approach]{Aims of Study and Analysis Approach}
The aim of this experiment is to test whether a harness architecture can make
adapter synthesis bounded, auditable, and reusable. The analysis evaluates
whether the pipeline separates the responsibilities of environment resolution,
contract specification, generation, validation, evidence recording, and
downstream use.

\subsection[Architectural Criteria]{Architectural Criteria}
The harness is analysed according to whether it separates generated code from
validation, exposes robot-and-runtime assumptions, supports repair feedback,
and preserves evidence for later interpretation.

\subsection[Boundary Criteria]{Boundary Criteria}
The generated adapter should remain a thin runtime-facing layer. The harness
should own contracts, success criteria, validation gates, repair feedback, and
evidence records. This boundary prevents the LLM-authored code from becoming
both the implementation and the judge of its own correctness.

\section[Harness Architecture Analysis]{Harness Architecture Analysis}
The harness coordinates the lifecycle of an adapter: resolving environment
information, presenting formal specifications, invoking generation roles,
running validation procedures, collecting evidence, and exposing artifacts for
downstream use or diagnosis.

\subsection[Environment Resolution]{Environment Resolution}
Environment resolution determines what the agent can rely on before generating
code. This includes available packages, runtime paths, simulator or hardware
availability, bridge endpoints, calibration locations, and backend
documentation.

\subsection[Robot Runtime and Transport Contracts]{Robot Runtime and Transport Contracts}
The contract layer specifies robot morphology, primitive semantics, action and
observation interfaces, backend route, and safety constraints. Transport
interfaces define the communication path to the backend, while runtime backends
name the concrete execution surface.

\subsection[Validation and Evidence Framework]{Validation and Evidence Framework}
Validation procedures produce evidence for source validity, importability,
primitive conformance, transport behaviour, composition behaviour, and
downstream usability. These procedures form a bounded evidence framework rather
than a guarantee of all physical behaviours.

\subsubsection[Success Criteria and Validation]{Success Criteria and Validation}

Industrial robot performance standards separate measurement procedures from
application-specific acceptance limits. ISO~9283 defines performance criteria
and related test methods for manipulating industrial robots, including pose
accuracy, pose repeatability, path accuracy, and path repeatability
\citep{iso9283}. It does not prescribe one numerical pass threshold for every
robot and application. ISO~9946 instead standardises how manufacturers present
robot characteristics \citep{iso9946}. For context, Universal Robots reports
UR5e pose repeatability of \(\pm 0.03\,\mathrm{mm}\) under ISO~9283, whereas
Franka Robotics reports less than \(\pm 0.1\,\mathrm{mm}\) for Franka
Research~3 under specified workspace and pose conditions
\citep{universalrobots2026ur5e,franka2026research3}. These figures are
manufacturer-reported repeatability specifications, not acceptance thresholds
adopted by this thesis. Repeatability describes the dispersion among repeated
visits to the same commanded pose and is distinct from absolute accuracy
\citep{messina2019target}. A single terminal endpoint error measured in
Direct MuJoCo is therefore neither an ISO~9283 repeatability measurement nor
evidence of industrial positioning accuracy.

The reach-success criterion used in this study comes from public
reinforcement-learning task definitions. At the pinned Meta-World commit,
Sawyer Reach v3 uses \(0.05\,\mathrm{m}\) as the Euclidean-distance
threshold between the tool centre point and its target
\citep{farama2026metaworldreach}. Farama FetchReach likewise uses
\(0.05\,\mathrm{m}\) as the Euclidean-distance threshold between the end
effector and its goal \citep{farama2026fetchreach}. Meta-World includes the
exact boundary, whereas the FetchReach documentation uses a strict
inequality.

This thesis therefore interprets \(0.05\,\mathrm{m}\) as a source-benchmark
task-completion convention, not as an industrial positioning tolerance. A
position-only binary result does not establish end-effector orientation,
stable dwell, collision-free execution, contact validity, or physical safety;
these properties require separate criteria and trusted guards. Reference-driver
endpoint errors are retained only as positive-control execution results. They
test whether the simulator, measurement binding, trusted Harness, and
reference controller can execute the declared task under the evaluated
conditions. They are not used to select, tune, or justify the acceptance
threshold, because deriving a threshold from those outcomes would make the
requirement depend on the calibration controller used to exercise it.

\section[Results]{Results}
The result of Exp. 1 is a harness formulation in which generated adapter
code is only one artifact inside a larger contract-governed process. This
structure supports clearer failure attribution, more explicit assumptions, and
more reusable adapter outputs than a one-off task script.

\section[Discussion]{Discussion}
The harness architecture provides the methodological foundation for the
remaining experiments. Its main limitation is that validation coverage defines
the boundary of the claim: an adapter can be shown to satisfy available
contracts and tests, but this does not prove unrestricted robot autonomy or
complete physical deployment readiness.
