\section{Introduction}

Large language models support task-level robot planning, yet high-level
controllers cannot translate abstract actions into robot-specific actuation.
Prominent methods advance skill selection, feedback-conditioned planning, and
policy-code generation, but commonly begin from supplied skills, motion
mechanisms, or control APIs
\citep{ahn2022saycan,huang2023innermonologue,liang2023codeaspolicies}. Recent
agentic systems use test, execution, or physical feedback to refine controller
and policy code
\citep{tripathi2026testdriven,xiao2026enpire,fu2026capx,lu2026aspire}.

This chapter presents Auto-Adapter, a framework that uses public robot
descriptions, a simulation model, and documented tasks to construct reusable
robot capabilities and a robot-specific Python driver. Task-Grounded
Capability Design identifies bounded operations shared across tasks; for
example, reaching and manipulation tasks may motivate an end-effector
capability whose success requires reaching and holding a target within a stated
tolerance. Before driver generation, an Independent Validation Compiler
converts these requirements into executable tests without access to the
eventual implementation. A ReAct coding agent then develops the driver by
reading permitted files, revising its artefacts, and running bounded Python and
simulation checks \citep{yao2023react}. Final acceptance uses simulator state
recorded independently of the generated code, rather than its return values or
self-reported success.

The chapter's central empirical objective is to establish whether Auto-Adapter
produces effective robot-specific drivers whose quality, operationalised as
matched-task success under the same fixed high-level controller, exceeds that
of the selected embodied-AI baselines. This comparison does not extend to
expert-written or manually tuned drivers. Its practical motivation is to reduce
integration effort and dependence on low-level robotics expertise, thereby
lowering the entry barrier for researchers specialising in high-level
language-model policies.

\section{Background}

\subsection{Physics-Grounded Feedback}

LLM coding agents use compiler and test failures as development feedback.
\citet{tripathi2026testdriven} return structured \texttt{pytest} diagnostics
that may include aggregate simulator measurements, while
\citet{kim2026physicalcorrection} use physical simulation to correct
LLM-generated tool-using primitives. The Auto-Adapter experiment asks whether
a bounded, candidate-visible projection of MuJoCo state adds information beyond
structured diagnostics. This public feedback remains distinct from the sealed
validation cases and final \emph{Harness} verdict, and simulator state does not
establish hardware behaviour.

\subsection{Capability Design}

Task-conditioned robot programming commonly generates the code or operation
needed for one instruction, potentially leaving other reusable operations
unexplored \citep{liang2023codeaspolicies,mu2024robocodex}. Task-Grounded
Capability Design instead supplies at least twenty source-backed tasks, without
a capability catalogue or task-to-capability mapping, and asks the model to
propose five to ten capabilities intended to cover the library. From the
associated task-level standards, the model also forms capability-level pass
criteria. An implementation-blind IVC audits whether those criteria preserve
source obligations, binds them to private MuJoCo task instances and trusted
measurement definitions, and compiles an executable validation suite; the
\emph{Harness} retains final verdict authority. This design is intended to give
the high-level controller a broader set of independently testable operations
to select and compose.

\section{Auto-Adapter Framework}

\subsection{Pipeline Overview}

Auto-Adapter operates on an isolated working directory containing public robot
documentation, a canonical MuJoCo model, and a library of source-backed tasks.
The pipeline proceeds through six ordered stages: STUDY, Task-Grounded
Capability Design, Independent Validation Compilation, driver generation,
capability validation and Repair, and Task Demo. Stage transitions are
controlled by the framework, whereas the work within each model-authored stage
is performed through an iterative ReAct process. The principal model-authored
artefacts are \texttt{study.json}, \texttt{capability\_design.json},
\texttt{capability\_validation\_suite.json}, and \texttt{driver.py}.

The stages separate three responsibilities. Capability design specifies which
task-neutral operations the robot should expose. Validation compilation
determines how the physical effects of those operations will be measured.
Driver generation implements the operations for the selected robot. Because
the validation cases are fixed before driver generation, the generated code
cannot define its own success criteria or determine the final verdict.

\subsection{ReAct Agent and Study}

Within each model-authored stage, a ReAct agent alternates between reasoning,
tool use, and revision \citep{yao2023react}. Its common interface contains
three tools: \texttt{read\_file} for inspecting permitted inputs,
\texttt{write\_file} for revising the stage artefact, and
\texttt{execute\_python} for running bounded Python and MuJoCo probes. Tool
outputs, including execution errors and simulator observations, return to the
same conversation so that the agent can revise its current artefact. The
Python session persists within the stage, although each execution remains
subject to path, time, simulation-step, and output limits.

STUDY uses this workspace to inspect the robot before either capabilities or
driver code are written. The agent examines the public documentation and
canonical model to identify joints, actuators, limits, body and site names,
coordinate conventions, and relevant control interfaces. It may load the model
and run bounded probes to confirm that the scene advances under actuator
control. The resulting \texttt{study.json} records these observations,
implementation constraints, and unresolved risks. It does not contain the
driver and cannot inspect the later validation cases.

\subsection{Capability and Validation Design}

Task-Grounded Capability Design uses the study and source-backed task library
to define between three and ten reusable capabilities. Each capability
describes one composable physical effect through a closed, task-neutral
request. The associated task records justify which tasks the capability may
support, but they do not prescribe an execution sequence, waypoint plan, or
complete task solution.

For example, reaching above an object, positioning the gripper for grasping,
and moving an object towards a destination all require controlled Cartesian
placement. These tasks may motivate an end-effector capability that accepts a
target position. Its criterion can require the measured end-effector site to
enter and remain within a stated tolerance of that target. The capability
therefore captures a reusable physical effect without embedding the identity
or action sequence of any one task.

Before driver generation, the Independent Validation Compiler converts each
capability criterion into executable simulation cases. It can inspect the
sealed capability design and private execution information needed to initialise
and measure a case, but it cannot inspect the eventual driver, its development
traces, or any Repair history. For every capability, it authors one nominal
request and one calibrated-boundary request near the declared operating limit.
In a formal run, both cases are first executed with a private known-working
driver. This positive control establishes that the compiled requests and
criteria are achievable in the canonical model before the suite is sealed.
The sealed cases are subsequently hidden from driver generation and Repair.

\subsection{Driver Generation and Physics-Grounded Feedback}

GENERATE begins with an interface-only \texttt{driver.py} containing the
required construction function and capability method signatures. The template
contains no robot-specific actuator mapping, controller implementation, task
dispatch, or validation logic. The ReAct agent reads the permitted robot
artefacts, writes an implementation, and uses \texttt{execute\_python} to run
public source, import, and simulation checks. It may inspect observations such
as joint positions and velocities, actuator commands, body or site positions,
and contacts before revising the code.

This creates a write--run--observe--revise development loop. A failed import,
an unexpected actuator response, or a large simulated tracking error supplies
concrete evidence for the next revision. These development simulations help
the agent debug its implementation, but they cannot issue an acceptance
verdict because they do not contain the sealed validation cases.

The experiment in this chapter uses skeleton-assisted generation. The agent
may inspect task-neutral controller structures appropriate to the robot
family, such as a generic Cartesian controller for a serial arm. A skeleton
does not provide the robot-specific joint or actuator mapping, task identity,
private thresholds, reset state, or verdict logic; these remain outside the
generated implementation.

During execution, a motion-producing capability reads the current
\texttt{mujoco.MjData}, computes actuator commands from the observed state and
public request, and writes them through \texttt{data.ctrl}. Subsequent MuJoCo
steps generate the evaluated trajectory \citep{todorov2012mujoco}. This
closed-loop interaction allows the implementation to respond to tracking error
and state changes rather than relying on a fixed command sequence.

\subsection{Independent Validation and Repair}

When GENERATE ends with a source- and import-valid \texttt{driver.py}, the
framework freezes an immutable copy as a driver attempt. Each validation trial
then loads the canonical MJCF into a fresh \texttt{mujoco.MjModel}, creates a
fresh \texttt{mujoco.MjData}, applies the prescribed reset, and executes the
driver in an isolated process. State acquisition remains outside the generated
code. As simulation advances, the evaluator samples \texttt{qpos},
\texttt{qvel}, and \texttt{ctrl}, together with named joint states, body and
site poses, and contact information.

The independently recorded trajectory is evaluated against the cases compiled
before generation. Driver return values, printed messages, textual
explanations, and self-reported success do not count as physical evidence.
Execution-integrity checks also reject direct modification of evaluated
positions, velocities, poses, contacts, or simulation time. Accepted motion
must instead arise from actuator commands followed by MuJoCo physics.

If a case fails, Repair receives the previous driver and a bounded report
containing the request, measured outcomes, available trajectory diagnostics,
execution errors, and guard results. The executable measurement logic and
other private case information remain hidden. Repair may modify only
\texttt{driver.py} and uses the same ReAct tools and public development
simulations as GENERATE. The protocol permits one initial frozen driver and at
most two repaired drivers. Files that fail the source or import checks are not
counted as submitted attempts.

\subsection{Task Demonstration and Scope}

Capability validation reports each capability separately. A capability becomes
available to Task Demo only when both its nominal and calibrated-boundary cases
pass. The final driver may therefore expose a truthful subset of validated
capabilities even when another capability fails. A separate task-level
controller may compose only this validated subset when attempting the
source-backed tasks.

Task completion is determined independently from the recorded MuJoCo state and
continuous execution video, rather than from the controller's declaration that
it has finished. The resulting evidence supports claims about simulated
capability execution and task completion only; it does not establish hardware
performance or sim-to-real transfer. Experiment~2 reported in this chapter
terminates after Task Demo and disables the optional Evolution stage, so no
later Experience proposal can affect its drivers or results.
