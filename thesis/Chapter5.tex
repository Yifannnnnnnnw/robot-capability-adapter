\chapter[Auto-Adapter Across Robots]{Auto-Adapter Across Eleven Robot Configurations}
\label{chapter:multi-robot-experiment}

\section[Introduction]{Introduction}

Extending a robot-software framework to a new platform usually requires a
robot-specific driver: a reusable Python interface that translates common
capability requests into platform commands. Experiment 3 applies Auto-Adapter
to eleven robot configurations under one fixed generation condition. Three
fresh runs per configuration produce 33 robot--replicate cells. In each cell,
Auto-Adapter generates a capability design, independently compiles its
validation criteria before driver generation, and permits an initial driver
submission followed by at most two Repair submissions. A driver that passes
the complete suite then enters a separate five-task Task Demo. The experiment
addresses RQ3 by reporting capability generation, driver validation and
downstream task completion. Its evidence is descriptive and limited to the
declared Direct-MuJoCo cohort; it does not isolate morphology as a causal
factor or establish hardware performance.

\section[Background]{Background}

Robotics software has long sought portability across platforms by separating
task logic from platform-specific execution. The Robot Operating System (ROS)
provided modular communication and shared software packages, while ROS 2
extended this architecture for distributed systems
\citep{quigley2009ros,macenski2022ros2}. Capability-based frameworks expose
robot functions as task-facing operations, and SkiROS2 organises these
operations into executable skills
\citep{pantano2022capabilitysurvey,mayr2023skiros2}. However, these abstractions
do not themselves supply the platform-specific control interface required by a
newly introduced robot. Auto-Adapter targets this integration step by
generating a driver behind a stable capability interface. Its longer-term aim
is to simplify future robot onboarding, whereas Experiment 3 examines this
route within a bounded simulator cohort.

A capability is a task-facing operation implemented by the generated driver.
Within each cell, Task-Grounded Capability Design (TGCD) defines the interface,
and the Independent Validation Compiler (IVC) compiles its
implementation-blind criteria before driver generation. The trusted Harness
then determines driver admission, after which only the admitted driver is
fixed for the separate Task Demo.

An initial whole-suite pass requires the first driver submission to pass every
cell-local criterion; final admission may occur on any submission within the
three-submission budget. A Repair conversion is an initial failure followed by
final admission. Both rates retain all three cells per configuration and all
33 cells overall, including cells that do not reach driver admission.

Task Demo statuses are mutually exclusive: P denotes a complete five-task
pass, F an executed Demo that does not pass, and NR a \texttt{not-run}
outcome. An F outcome does not by itself attribute the failure to the
candidate. Terminal failure classes are recorded separately; an
infrastructure failure is therefore reported in the failure-class column
rather than as a fourth Demo status.

Task success is the number of passed tasks divided by the number of
independently evaluable tasks and is reported as \texttt{N/A} when that
denominator is zero. Coverage is $\mathrm{evaluable}/(5 \times A)$, where $A$
is the number of final-admitted cells. An NR outcome contributes no passed or
evaluable tasks.
